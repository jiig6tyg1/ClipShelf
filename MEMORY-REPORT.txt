ClipShelf — メモリ最適化の測定結果
測定日: 2026-10-04（日本時間）
環境: Apple Silicon / macOS 27.0.1 (26A434), Swift 6.4, swiftc -O

結果（物理フットプリント、MiB = 1,048,576 bytes）
状態               最適化前    最適化後
空の履歴              21.1       21.2
画像20枚投入          88.1       72.0
画像80枚投入         287.2       72.1
画像160枚投入        290.5       72.1
履歴クリア直後       234.2       72.1

160枚投入時は約75.2%削減。80枚から160枚へ投入を増やしても、最適化後の値はほぼ横ばいでした。

比較条件と限界
・同じ乱数シードの1024×1024 RGBA画像をPNGに変換し、末尾に一意のマーカーを付けて160回投入。
・同じClipboardStoreを独立した名前付きクリップボードに接続。一般のクリップボードや実ユーザーの履歴は使用しません。
・永続保存はオフ。画像描画UIを含まない履歴処理のベンチマークです。
・task_info(TASK_VM_INFO)のphys_footprintを取得。RSSや仮想アドレス空間の大きさとは異なります。
・各バージョン1回の同条件測定です。OSのキャッシュ、画像の内容、表示状態などにより数値は変わります。
・旧版は80枚（合計263.0 MiB）を保持。新版は48 MiB制限により14枚（合計46.0 MiB）を保持しました。
・画質を落として原本を保持する手法ではありません。原本の容量上限に達したら古い未ピン留め項目を削除する仕様変更です。
・クリア直後もmallocやOSキャッシュがページを保持するため、RSS／フットプリントは直ちに空の履歴と同じにはなりません。
・別途、新版の実GUIアプリをテキスト履歴で起動した時点のvmmapでは物理フットプリント30.0 MiB、ピーク30.2 MiB、psのRSSは約108.6 MiBでした。この値は上記ベンチマークとは比較できません。
・全プロセスの最大メモリを保証するものではありません。保存中は1件の処理中スナップショットと最新1件、エンコード領域などが追加で必要になります。

変更点
1. 履歴合計48 MiBの容量上限を追加。件数上限80件との両方を満たすまで整理。
2. ImageIOで縮小してから表示。512px上限、12 MiBのLRUキャッシュ。非表示になったカードは画像参照を解放。
3. メモリ警告時は縮小画像キャッシュを解放。
4. コピー時は原本のPNG／TIFFデータをそのまま使用し、NSImage経由の再エンコードを回避。
5. JSON/Base64からバイナリplistへ移行。バックグラウンド・直列・最新要求への集約により保存要求の無制限な積み上がりを防止。
6. 起動時の保存ファイルサイズ、画像バイト数・画素数、件数・容量を検証。
7. テキストプレビューを600文字に制限し、巨大テキスト全体のレイアウトを回避。
8. タイマーに許容誤差を設け、不要な厳密タイミングのウェイクアップを抑制。

再現

CSV生データ: Benchmarks/before.csv と Benchmarks/after.csv

現行ソースには最適化後の実装を収録しています。

検証
・既存の履歴、検索、重複排除、機密形式除外、保存、ショートカット、位置補正、上下キー移動。
・非同期保存で最新スナップショットが残ること、保存オフが先行する書き込みに負けないこと。
・40枚の縮小画像で512px／12 MiBの上限を維持し、キャッシュを解放できること。
・画像原本の合計容量制限と、整理時のピン留め保持。
・不正な画像データの拒否。
